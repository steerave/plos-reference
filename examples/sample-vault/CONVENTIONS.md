# PLOS Conventions

This document holds the operating rules of the PLOS vault — how the system routes questions, how facts get merged, how files are named, what shape entity records take. It is referenced by `CLAUDE.md` (in this same directory) but kept separate from it: `CLAUDE.md` is development guidance for an agent operating on the vault, this is the operating rules of the vault itself.

## File-structure split: where the rules live

Three top-level documents in the vault, each with a distinct job:

- **`CLAUDE.md`** — agent-facing development guidance. Where things live, what to edit, what not to touch, naming conventions, anti-patterns, how to extend the system. Stable; rarely changes once written. Loads automatically when Claude Code operates on the vault.
- **`CONVENTIONS.md`** (this document) — the operating rules of the system. Decision rules, resolution rules, schema, frontmatter contract. Changes when architecture evolves.
- **`INDEX.md`** — the answer key. Maps recurring questions to their answer surface (compiled artifact or Dataview dashboard).

`CLAUDE.md` references this document for any question of the form "how does the system actually decide X." Anything specific to operating the system goes here, not in `CLAUDE.md`, so that development guidance stays separate from architectural rules.

## The routing decision rule

Every recurring question PLOS answers is routed to one of two surfaces. The default and the exception are stated as a simple rule:

> **Default:** Dataview at view-time for any cross-entity view, aggregation, filter, or sort.
> **Exception:** Compiled artifact only when the answer requires synthesis beyond aggregation — priority reasoning, anomaly detection from patterns, or gap-surfacing against an expected-document checklist.

The current set of compiled artifacts (named exceptions): `this-week.md`, `anomalies.md`, `tax-prep.md`. Each is justified individually in `INDEX.md` and in the architecture document at the repo root.

**Rule for adding a new compiled artifact:** must satisfy at least one of the synthesis criteria above (priority reasoning, pattern detection, or checklist-vs-received gap surfacing) AND require capability Dataview cannot provide. Add the new exception with explicit rationale; update `INDEX.md`; update this document if the rule itself needs refinement.

**Rule for new questions:** if the question is "show me all X where Y," it's Dataview. If it's "tell me what X means in context of Y" or "what's missing that I expected," it's compiled. When in doubt, start as Dataview — it's reversible (promoting a Dataview dashboard to a compiled artifact is just adding a synthesis layer; the reverse is more work).

## The merge resolution rule

When multiple sources produce values for the same entity field at different times, the resolution rule determines which value the entity record holds:

1. **Corrections always win.** A correction recorded in `corrections.md` for a given entity+field beats every other source.
2. **Locked fields are bypassed.** If the field name appears in the entity's `locked_fields:` frontmatter list, the existing value is preserved regardless of new extractions. The extraction is still recorded for audit.
3. **Otherwise, freshness wins.** Rank candidates by `COALESCE(data_effective_date, document_date)`. A future effective date (insurance renewal letter for July coverage) outranks a current document date.
4. **Tie-break** by extraction confidence, then by extraction timestamp.

Hand-edits to frontmatter that are NOT in `locked_fields:` and NOT recorded in `corrections.md` may be overwritten by a fresher extraction. This convention is the user's part of the contract. Two override mechanisms preserve hand edits:

- **`locked_fields:` frontmatter list** — lightweight per-entity protection. Add a field name; future extractions skip it.
- **`corrections.md`** — vault-wide override file with provenance. Edit, run `import_corrections.py`, future merges treat the correction as authoritative.

## Frontmatter contract

Anything compile passes filter on, sort by, or surface in summaries — and anything Dataview queries against — must live in YAML frontmatter as a typed field. Anything narrative goes in prose.

When in doubt, frontmatter. It's cheaper to read structurally than to parse prose.

Common frontmatter conventions:

- `type:` always one of `source`, `compiled`, `dashboard`.
- `entity:` for source records: `property`, `vehicle`, `person`, `account`, `organization`, `tax_year`, `project`.
- `slug:` short, kebab-case identifier matching the folder name.
- `status:` lifecycle marker: `active`, `archived`, `sold`, `retired`. Defaults to `active`.
- Date fields: ISO format (`YYYY-MM-DD`) for any date Dataview will filter on.
- Money fields: numeric only (no currency symbols). Currency is implied unless the entity record states otherwise in `currency:`.
- Cross-references: wikilinks (`[[123-main-davenport]]`) for entities; relative paths (`mortgage/current-statement.txt`) for documents.

Adding a new frontmatter field: pick a name that's specific (`mortgage_servicer_current` not `servicer`), use it consistently across entities of that type, and update `_schema/` if the field is part of a domain schema.

## Naming conventions

- **Slugs are kebab-case.** `123-main-davenport`, `2019-civic-1234`, `chase-checking-4521`.
- **`current-X` for whatever is in force right now.** `mortgage/current-statement.pdf`, `insurance/current-policy.pdf`. Past versions move to `archive/` subfolder.
- **Extracted text sits next to the original.** `policy-2025.pdf` and `policy-2025.txt` (or `.md`) both kept. Originals are immutable.
- **One entity per folder.** The folder is the entity. `index.md` is the entity record at the folder root.

---

## Lifecycle: archived entities

When a property is sold, a vehicle is retired, an account is closed, or a person's record needs to be frozen, the entity folder moves from `source/<domain>/<slug>/` to `source/archive/<domain>/<slug>/`. Frontmatter `status:` flips to `archived` (or more specifically `sold`, `retired`, etc.) with a `status_changed` date.

Compile passes and Dataview queries read `source/<domain>/` by default and ignore `source/archive/` unless explicitly told otherwise. This keeps current snapshots clean while preserving history for tax, audit, and continuity-of-records purposes.

## What this document is not

- Not the architecture document. The runtime architecture (worker, capture flow, four runtime components) lives in `ARCHITECTURE.md` at the repo root. This file is conventions inside the vault.
